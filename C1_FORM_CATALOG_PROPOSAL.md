# C1 form catalog and job forms — proposal for review

Status: **proposed; not approved or implemented**. This is a contract for a future forward-only migration and application changes, not evidence of an issued certificate or a completed C1 workflow. Migration 0012 is present in commit `66b4f9d`; the repository does not establish its deployment history. Treat it as potentially applied everywhere and do not edit it. Confirm migration ledgers for each intended environment through separately authorized read-only operations before deployment planning. No persistent database was inspected for this proposal.

## Data model

All IDs are generated by the server. Workspace ownership is enforced on every lookup and mutation, including referenced records. Composite foreign keys or equivalent constraints must prevent cross-workspace and cross-brand associations. Timestamps and actor IDs are server assigned. The following names describe proposed new tables, not existing schema:

- `form_definitions`: id, workspace_id, brand_id (or explicit workspace-wide scope), code, title, description, category, lifecycle status, published_revision_id, created/updated metadata. Unique code per workspace. Archiving must not invalidate existing references; delete only an unreferenced draft definition.
- `form_revisions`: id, workspace_id, definition_id, version label, state (DRAFT, REVIEW, PUBLISHED), schema version, creator, reviewer/approver and timestamps. A revision ID, never its label, identifies transitions and references. Published content and children are immutable; publication atomically changes the parent's published pointer only after authorized review. Drafts are independently discoverable.
- `form_sections`: id, revision_id, title, description, order and repeatable flag. `form_fields`: id, section_id, stable key, label, instruction, order, type, required, choices, validation and approved auto-fill mapping. Validate unique keys, type-specific configuration, allowed mappings, sizes and choice values on the server. Supported controls: text, number, date, dropdown, checkbox, multiple choice, pass/fail, repeatable table, photo and signature. Version the schema and validation semantics; reject unsupported types rather than silently treating them as text.
- `policy_form_rules`: id, workspace_id, policy_revision_id, form_definition_id, form_revision_id, required, order and optional condition in a versioned, constrained expression language. Publication validates that referenced revisions are published, in scope and applicable. Freeze rule and condition semantics with the policy; reject direct-to-invoice when required rules apply. Do not interpret an empty selection as a statutory determination.
- `job_form_instances`: id, workspace_id, brand_id, job_id, form_revision_id, policy_revision_id and immutable policy/rule snapshot, origin (mandatory, optional policy, or additional), structured answers, status and concurrency version. Additional forms cannot replace or delete mandatory instances. Auto-fill records values at creation, with provenance, using an explicit allowlist; validate later edits by field type and policy.
- `job_form_events`: append-only actor, time, action and immutable snapshot/hash or version reference for edits, validation, signatures and explicit authorized waivers. Waivers capture actor, reason, scope and time, are allowed only by an approved policy, and never silently satisfy a non-waivable requirement. Signatures bind signer and time to the exact canonical answer/evidence snapshot. Any subsequent change invalidates sign-off and verified completion. Only server validation may set completion; missing required values, evidence or signatures block it.
- `job_form_attachments`: workspace/job/instance ownership, immutable object reference, media metadata, checksum, uploader and time. Object authorization, upload verification, size/type limits and lifecycle must be enforced by the service. Never expose storage keys as public access grants.
- `generated_documents` and delivery events: workspace, brand, job and form-instance/revision references; immutable content hash, versioned private object key, media type, generation status and actor/time; retention class and hold/deletion state; delivery attempt/channel, authorized recipient reference, provider outcome and timestamps. Generation, storage and delivery are distinct states; only a confirmed provider result establishes delivery. Retention periods, provider and customer consent/access policy require owner approval. Browser print and sample filenames establish none of these states.

Existing `demo_jobs` are demo-scoped; production job ownership and lifecycle must be confirmed before choosing a foreign key target. This proposal does not authorize a production job model or storage provider.

## Compatibility and rollout

1. Take an authorized backup and inventory migration ledgers, legacy rules, active pointers and existing job snapshots on each target. Resolve mismatches before any execution. No remote or shared D1 writes are authorized by this document.
2. Add new tables and constraints in a separately reviewed migration after exact-file and schema approval. Leave 0012, its legacy tables and existing records unchanged. Do not disable immutability protections. Atomic migration and rollback/recovery procedures must be validated against disposable D1/workerd first.
3. Map each legacy code to a distinct definition and approved revision only after the client-supplied JSA, CoTC, Smoke Alarm, TCA1 and TCA2 sources and their provenance are inspected and reviewed. Preserve original evidence; do not infer statutory obligations from seed text. Existing policy rows and historical jobs remain unchanged. Record mappings and provenance; ambiguous mappings require review, not automatic publication.
4. Backfill new rule references by immutable policy ID only when mapping is approved, with row counts and reconciliation. Unmapped legacy rules continue through an explicitly tested compatibility reader; never silently omit a mandatory rule. New policies use catalog references. Do not mutate published legacy rules. Existing jobs retain their recorded requirements; where history is absent, flag for review rather than fabricate it.
5. Deploy readers before switching writers, with a controlled feature gate and reconciled rollback. New-job creation snapshots the effective published policy and instances atomically. A rollback must preserve new data and must not fall back to a reader that ignores custom mandatory forms; stop affected creation/completion if compatibility cannot be guaranteed.

## Proposed API and authorization

Under `/api/v1/workspaces/{workspace}`: list/create definitions; retrieve a definition and revision history; create/update/delete unreferenced draft revisions; preview a draft with representative non-sensitive data; submit revision for review; approve/publish; archive. List published definitions filtered by brand and authorization. Return authoritative IDs and versions from every successful write. Server enforces role and workspace checks for every operation, not just UI controls.

Job-type policy endpoints create and edit a draft with full rule set and completion rule, retrieve draft/history, submit and approve/publish. Draft edits never alter the effective pointer. Publish validates all references and performs the transition and pointer swap atomically, with concurrency checks. Existing policy and form revisions remain immutable. The UI keeps unsaved edits local, reports success only after a successful response and reloads the returned authoritative record; errors remain visible and do not imply success.

Job endpoints create/list instances, add an authorized additional form, save structured answers and attachments with optimistic concurrency, validate, sign, and request/approve a permitted waiver. Server checks job ownership, revision and policy snapshots, validates every field and signature, and gates completion against all mandatory requirements. Document endpoints request generation, inspect status and authorized metadata, and record controlled delivery attempts. No endpoint may treat a print action as issuance or delivery. Exact HTTP methods, request and response schemas, error codes, limits, authorization matrix and idempotency semantics require implementation review before approval.

## Verification required before acceptance

Use source-specific regressions and disposable local databases plus workerd tests for: custom form lifecycle and reload; roles, workspace isolation and authoritative IDs; immutable published content and active pointers; catalog filtering and policy persistence; existing-job snapshots and new-job inheritance; additional forms; type validation, signature invalidation, mandatory completion and authorized waiver; failures without false UI success; and document ownership/status. Exercise G03–G05 and PR #35 security regressions. Capture the requested end-to-end browser chain against an authorized local Worker and disposable database. Obtain separate approval before migration execution, protected-file edits, deployment, or any persistent schema change. No such approval is implied by this proposal.
